# Document Compare: pilot test plan

For application version 1.0.21.0, team package refreshed 15 October 2026. This is a plan for the team to run; the supplied results log starts as **Not run**. It contains 44 scenarios. Prior checks on the development PC are recorded separately in `VALIDATION.md`; these do not mark the team's log as passed.

## How to run the pilot

1. Start with three to five colleagues covering the team's actual Windows/Word configurations and both EP and WF work. Use a standard company account and the complete shared ZIP download/install process.
2. Run the controlled Word examples below first. Then use approved copies of representative real jobs, covering the document types in the next table. Keep original jobs unchanged and give test outputs their own folder in an approved local or shared location.
3. The app checks actual source-text languages before Word comparison. A known mismatch stops the job; Unknown/Mixed stops for manual review. Check matching relevant source languages before using **Language checked — compare** to retry an uncertain result. For every successful comparison, check the figures in the app and companion TXT summary, then open the DOCX in Word and select **Review > All Markup**. Inspect the first, middle and last parts, every changed area, and the Description/Claims boundaries in EP.
4. Record each run in `PilotResults.csv`. For EP, record Description, Full specification and Claims separately. For Batch or Multi Archive, also review the automatically saved `batch-results.csv` or `multi-archive-results.csv` and copy template rows for individual pairs where needed. The editable pilot log and generated comparison report are different files. Use an internal reference for the job; keep document text and confidential filenames out of general support messages.
5. Repeat problem cases after any fix, and repeat the controlled examples on the revised release. Keep the pilot release version fixed while comparing results between users.

Each run should record: tester/date, app version, Windows/Word versions, WF or EP, input formats, whether OCR was selected, source reference, expected and actual figures, runtime, warnings, output checked, and pass/fail or an issue number. Copy log rows for extra jobs; never change a previous result to imply an unperformed retest.

## How to judge the numbers

- Crossover = 100 x (new words - insertion words) / new words, displayed to one decimal place. Deletions are outside the new text. Word-recognised moved text is retained.
- In EP, Full specification new words and insertion words must each equal Description plus Claims. Calculate its percentage from those combined counts; do not average the two section percentages.
- The app's token rules can differ from Word's status-bar count. Use the supplied fixtures for exact reference values, then the documented counting rules for real jobs. Literal numbers count as words; automatically displayed list numbers may not be stored as text.
- Existing yellow highlighting does not establish that text was inserted by this comparison. Inspect the tracked insertion, not colour alone.
- An unavailable crossover with a reconciliation warning requires review; it is not 0%. Empty WF new text has unavailable crossover. EP requires nonempty Description and Claims.
- OCR errors and PDF reading-order/line-break changes can affect counts and matching. Inspect recognised text independently even if two recognised copies match perfectly.

## Known boundaries to check explicitly

Language detection uses actual text and runs locally through Windows ELS. It does not establish a match from Word's proofing-language setting. In EP, Description and selected original-language Claims are checked separately; covers, drawings and later translated claims are outside the check. Short technical text, mixed languages or unavailable detection may require the manual-review retry. Do not interpret Unknown/Mixed as a language match or use the retry when the relevant source languages differ. DOC/PDF/OCR may need conversion first, but the check still precedes Word comparison.

Batch comparison uses the visible file order, not file modification dates or an inferred publication chronology. Every later file is new against every earlier archive, giving n x (n - 1) / 2 pairs. Inputs are read directly from the selected folder; keep them unchanged during the run. A batch uncertainty pauses one pair for Language checked — continue or Skip pair; confirmation is not a blanket waiver for later pairs. Failed and unfinished report rows have blank metrics, not zero. Completed outputs are deliberately retained after cancellation or errors. Save completed pilot-log copies separately; installation preserves an existing log, so use the fresh release template to add the new batch cases.

EP expects standalone Description/Beschreibung followed by Claims/Ansprüche/Patentansprüche/Revendications and a supported first numbered claim (1., 1), (1), or Word numbering). It selects the first recognised claims section after Description; reviewers must confirm this is the intended original language. Separate drawings/references need recognised boundaries. Tables/inline figures inside the retained description are not the same as a separate excluded drawing section.

PDF conversion can merge headings or alter two-column reading order. Use WF when the EP new file is PDF or PDF-converted Word, with both copies prepared to the same intended scope. Remove covers, later translated claims and separate drawings where appropriate; WF does not remove them automatically and counts all included text. EP remains available for checked native Word specifications. OCR uses an installed language, preferring UK English then US English; it is not a per-page language selector. Scanned text inside ordinary Word images is not recovered by the PDF OCR checkbox. Record preparation/transcription requirements for such jobs.

Shared-drive sources and results are supported through UNC and mapped-drive paths when the current account can read/write them and the connection is available. OneDrive results may sync. Follow company access, retention and backup rules. Comparison/OCR and private working folders remain local; accepting a shared results folder does not make that folder private or offline.

When a test intentionally supplies an unsupported input, a clear safe refusal can be a pass. If common real jobs consistently need substantial preparation or produce unusable recognised text, record that as a workflow limitation and decide whether the workaround is acceptable before expansion.

## Pilot release decisions

Before inviting the pilot: controlled examples produce the reference results on the pilot configurations; local installation/launch works; sources are preserved; outputs open in Word; confidentiality/storage requirements and package execution are accepted by the responsible IT owner. Choose a support contact and keep one approved package in the shared location.

Before wider rollout: finish all applicable cases for the supported document families; involve at least three users; independently review the representative EP/PDF/OCR jobs; close and retest issues affecting metrics, missing retained text, incorrect EP boundaries, confidentiality, source/output preservation or unrelated Word work. List acceptable preparation/OCR limitations with an agreed user procedure. Mark an irrelevant test Not applicable with a reason, not Pass.

Use a short agreed pilot period (for example one working week). Record job volumes and runtimes for short/typical/large files so the team can decide whether responsiveness is acceptable; the app has a 20-minute limit per job. A useful completion measure is that every intended document family has demonstrated correct, reviewable results on the actual team environment, rather than a percentage pass rate that hides a critical failure.
